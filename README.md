# Separating Delivery and Regression Testing in Azure DevOps pipelines for independent executions.

# 3PL — Cypress Pipeline Architecture

**CI/CD Pipeline Refactoring | Cypress | Azure DevOps | YAML | JavaScript**

## Project Overview

Refactored the 3PLICITY Frontend Azure DevOps pipeline to separate application delivery from on-demand regression testing.

We took this as a standard to follow for subsequent projects.

The implementation preserves the existing delivery workflow while introducing an independent manual pipeline that runs Cypress against an already deployed environment. Both pipelines share a reusable YAML template, reducing duplicated configuration and keeping test execution consistent across scenarios.

### Key Contributions

- Extracted Cypress execution and reporting steps from the main pipeline into a reusable YAML template.
- Created an independent manual regression pipeline with DEV/PROD environment selection.
- Added a configurable execution mode to run tests against either a locally served build artifact or an already deployed application.
- Preserved report, screenshot, and JUnit result publishing through Azure DevOps.

## 1. Architecture Before and After

### Original architecture

Cypress configuration was embedded directly in `azure-pipelines.yml` and coupled to the delivery workflow.

```text
Build
  ↓
Publish vite-dist
  ↓
Serve application locally
  ↓
Run Cypress
  ↓
Publish test results
  ↓
Deploy DEV / PROD
```

This worked for validating a newly generated build, but did not provide a separate pipeline for running regression tests against an existing deployment.

### Refactored architecture

The implementation separates pipeline orchestration from reusable Cypress execution.

```text
azure-pipelines.yml
  Build → Cypress → Deploy
                 ↘
             Shared template
                 ↗
cypress-pipeline.yml
  Select DEV / PROD → Cypress → Reports
```

The three YAML files have distinct responsibilities:

| File | Responsibility |
|---|---|
| `azure-pipelines.yml` | Build the application, invoke Cypress and manage DEV/PROD deployment stages. |
| `cypress-pipeline.yml` | Provide a manually triggered regression pipeline with environment selection. |
| `templates/cypress-tests.yml` | Centralize Cypress setup, execution, environment configuration and result publishing. |

## 2. Reusable Cypress Template

The shared template accepts three parameters:

```yaml
parameters:
  - name: useLocalBuild
    type: boolean
    default: true

  - name: baseUrl
    type: string
    default: "http://localhost:8080"

  - name: environment
    type: string
    default: "dev"
```

This configuration allows both pipelines to reuse the same test execution logic without requiring separate implementations.

### Local build mode

The delivery pipeline passes `useLocalBuild: true`.

```yaml
- template: templates/cypress-tests.yml
  parameters:
    useLocalBuild: true
    baseUrl: "http://localhost:8080"
    environment: "dev"
```

In this mode, the template:

1. Downloads the `vite-dist` artifact generated by the Build stage.
2. Installs `serve` and `wait-on`.
3. Serves the built application on port `8080`.
4. Waits for the application to become available.
5. Installs Cypress dependencies and runs the tests.

This allows Cypress to validate the build artifact before the deployment stages consume that artifact.

### Deployed environment mode

The manual regression pipeline passes `useLocalBuild: false`.

```yaml
- template: templates/cypress-tests.yml
  parameters:
    useLocalBuild: false
    baseUrl: "https://app.3plicity.com"
    environment: "prod"
```

When this mode is selected, the template skips downloading the build artifact and starting a local server. Cypress runs against the supplied `baseUrl`, targeting the already deployed application.

The environment-specific URL and configuration are provided by the calling pipeline rather than hardcoded into the shared template's execution logic.

## 3. Manual Regression Pipeline

The new `cypress-pipeline.yml` is configured to run manually:

```yaml
trigger: none
pr: none

parameters:
  - name: environment
    displayName: "Environment"
    type: string
    default: "dev"
    values:
      - dev
      - prod
```

When starting a run in Azure DevOps, the user selects the target environment.

| Environment | Target |
|---|---|
| DEV | `https://delightful-ground-005697610.5.azurestaticapps.net` |
| PROD | `https://app.3plicity.com` |

The selected environment determines the template parameters and the corresponding environment-specific Cypress variables.

The pipeline does not build or deploy the application. Its purpose is to run regression tests against the selected deployment and publish the results.

**Practical benefit:** regression testing can be initiated independently of a new application build, making the pipeline available for QA and other team members who need to validate an existing environment.

## 4. Delivery Pipeline Integration

The main pipeline retains its existing Build, Test and Deploy stages.

```text
Source branch
     ↓
Build Vite application
     ↓
Publish vite-dist
     ↓
Run Cypress through shared template
     ↓
Deploy the same artifact
```

The Build stage uses Node.js 20 (npm) and selects the appropriate build command:

- `dev` → `npm run build:dev`
- `main` → `npm run build:prod`

The resulting `dist` directory is published as `vite-dist`.

The Cypress stage then invokes the shared template with `useLocalBuild: true`. The deployment stages download the published artifact and deploy it to the corresponding Azure Static Web App.

This preserves the intended delivery sequence: test the generated build before allowing the deployment stage to proceed.

## 5. Reporting and Test Results

The shared template centralizes the output publishing steps for both pipelines.

| Output | Implementation | Purpose |
|---|---|---|
| Cypress reports | Published as a pipeline artifact | Review generated test reports. |
| Screenshots | Published as a pipeline artifact | Inspect captured evidence from test runs. |
| JUnit results | `PublishTestResults@2` | View test results in the Azure DevOps Tests tab. |

The JUnit test run titles distinguish between `Cypress E2E (dev)` and `Cypress E2E (prod)`.

The publishing steps use `succeededOrFailed()` or `always()` conditions where configured, allowing result artifacts and test results to be published even when test execution fails.

## 6. Technical Challenges and Solutions

### Separating execution logic from pipeline orchestration

**Challenge:** Cypress setup and execution were embedded in the delivery pipeline, making independent regression runs difficult to maintain.

**Solution:** Extracted the common steps into `templates/cypress-tests.yml` and parameterized the differences between local-build and deployed-environment execution.

### Supporting two execution contexts

**Challenge:** Delivery testing requires the newly generated build, whereas manual regression should target an existing deployment.

**Solution:** Introduced `useLocalBuild` and `baseUrl` parameters. The same template can now either serve `vite-dist` locally or test a deployed application directly.

### Selecting the appropriate environment

**Challenge:** DEV and PROD use different application URLs and Cypress configuration values.

**Solution:** Added an environment parameter to the manual pipeline and used conditional template inclusion to supply the appropriate URL and environment configuration.

### Handling Azure DevOps template conditions

**Challenge:** Conditional template inclusion needed to be expressed using Azure DevOps compile-time syntax.

**Solution:** Used `${{ if }}` expressions to include the appropriate DEV or PROD template configuration based on the pipeline context.

## 7. Results and Limitations

### Results

- Separated delivery execution from on-demand regression testing.
- Centralized Cypress setup, environment configuration and reporting in one reusable template.
- Enabled manual selection of DEV or PROD for regression runs.
- Preserved build-artifact validation before deployment in the delivery workflow.
- Reduced duplicated pipeline configuration and made future Cypress pipeline changes easier to maintain.

### Known limitations and follow-up considerations

- **Pull request validation:** The main YAML declares PR triggers, but the Cypress template inclusion conditions compare `Build.SourceBranch` with `refs/heads/dev` and `refs/heads/main`. PR validation runs can use a `refs/pull/...` reference, so Cypress may be omitted during those runs. This behavior should be addressed and take needed assistance through AI such as Cursor if Cypress is required for PR validation.
- **Credential management:** The current template should include credentials as a secret Azure DevOps pipeline variable before the configuration is treated as production-ready.


## Technical Takeaway

This project demonstrates practical CI/CD pipeline refactoring: identifying tightly coupled responsibilities, extracting reusable YAML, parameterizing execution behavior and separating continuous delivery from independently triggered regression testing.

The work involved adapting the existing pipeline architecture rather than replacing it, while using AI-assisted development as a support tool for implementation and troubleshooting.
